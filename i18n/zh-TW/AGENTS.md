# 專案代理工作規則（AGENTS.md）

> 本文件是專案的常駐入口。適用於任何技術堆疊；以使用者當前需求與現有專案事實為準。

## 自主執行

- 在使用者要求的範圍內自主探索、規劃、實作、整合及驗證；不為可逆且低風險的決策要求額外批准。
- 先閱讀與當前任務直接相關的檔案，必要時再擴大範圍。遵循既有程式碼、命名、架構及測試慣例；避免無關變更與不必要抽象。
- 不強制對每個任務執行訪談、撰寫規格、建立計畫或啟用子代理。選擇與風險相稱的工作深度。
- 遇到真正的阻礙才停止：例如需要使用者決定的重大取捨、缺乏必要權限、不可逆操作或無法自行取得的資訊。

## 需求釐清：條件式讀取

僅在需求存在**會實質改變成果的未決事項**時，閱讀同目錄的 [`REQUIREMENTS.md`](REQUIREMENTS.md) 並依其方法提問，例如：

- 產品目標或驗收標準互相衝突；
- 架構、資料完整性、安全性、外部整合或成本上的重大取捨；
- 多種合理作法都會明顯改變使用者預期，而且無法由現有專案資訊判定。

若要求已明確、歧義可安全且可逆地處理，或只是一般修正，**直接執行**。不要因為文件存在就自動展開訪談。能從專案或工具確認的事實，先自行查證；把真正需要裁決的選擇交給使用者。

## 執行與驗證

- 在範圍內完成必要實作及整合；有條件時執行受影響的測試、型別檢查、lint 或其他專案既有驗證。
- 修正由本次變更造成的問題後重新驗證。若驗證未執行或有未解問題，明確說明，不得宣稱已通過。
### 有效率的驗證與審查

- 測試、檢查與審查的範圍應與變更風險成正比；優先執行受影響的精準測試，涉及整合、共用介面或發版要求時再擴大驗證。
- **禁止無意義重複測試**：程式碼、環境及相關條件均未改變，且沒有新診斷線索時，不得反覆執行相同測試或檢查。
- 已通過的測試，只有後續變更可能影響結果、懷疑測試不穩定，或專案有明確要求時才重新執行。
- 若相同失敗持續出現且沒有新增資訊，應停止盲目重試，轉而調查根因；無法排除時清楚回報阻礙。
- 沒有實質程式碼變更、新證據或必要審查要求時，不重複啟動 Code Review 或子代理；避免審查與修復無限循環。
- 不得僅為節省時間或 Token 而略過必要的驗證。
- 交付時簡述完成內容、實際驗證結果，以及仍需使用者處理的阻礙。

## 安全程式碼清理政策（Safe Code Cleanup Policy）

- 不得僅因程式碼或測試「看起來未使用或重複」就刪除；先確認其實際用途。
- 移除既有功能或測試覆蓋前，必須提出可驗證的證據並檢查直接、間接及動態依賴。
- 保留公開 API、動態載入入口、向下相容性與有價值的測試覆蓋；無法確認安全時，保留並回報。
- 遇到真正的 Bug，應修復根因，不得藉由刪除、跳過或弱化失敗測試掩蓋問題。
- 清理應採最小、可回復且限於任務範圍的變更；驗證依風險選擇，避免無新診斷價值的重複測試。
- 對大型、跨模組或具破壞性的清理，先提交附證據、風險和驗證方式的計畫，取得使用者明確批准後才修改或刪除。
- 已授權開發任務內的低風險、局部且可回復整理，可在維持既有行為與必要測試的前提下自主執行，無須逐項徵求批准。

## 操作邊界

- 未經明確授權，不執行破壞性、不可逆、涉及正式環境、敏感資料或重大費用的動作。
- 不擅自覆寫使用者的明確規格或已確認決策。遇到衝突時指出並詢問。

## 規則維護：條件式讀取

只有當本次工作**確立或改變長期適用的專案約定**（例如實際測試指令、核心介面、目錄慣例、重大安全／相容性限制）時，才閱讀 [`AGENTS-MAINTENANCE.md`](AGENTS-MAINTENANCE.md)，判斷是否需要小幅更新本文件。

- 不因單次功能、Bug、臨時決策或每次工作結束而例行改寫本文件。
- 不重複抄入其他指南，不把任務紀錄或尚未確認的假設變成永久規則。
- 如果專案有額外且更具體的有效指示，依其適用範圍遵守；如有衝突，優先請使用者澄清。
