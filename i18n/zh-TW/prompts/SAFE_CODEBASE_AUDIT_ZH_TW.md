# 程式碼庫深度稽核與安全清理（Deep Codebase Audit & Safe Cleanup）

> 適用於 Codex 的單次深度清理任務。這不是要求模型追求最大刪除量，而是以具體證據改善可維護性，並降低回歸風險。

## 任務目標與核心原則

請對目前專案進行全面但保守的程式碼庫健康檢查，識別可以安全清理的技術債、遺留程式碼、重複實作與冗餘測試。

**正確性與功能完整性優先；證據優先於刪除；最小必要變更優先於清理數量。**

## 第一階段：理解專案（唯讀）

1. 閱讀專案中的 `AGENTS.md`、`REQUIREMENTS.md`、`AGENTS-MAINTENANCE.md` 與相關文件（若存在），遵守既有規範；若規範衝突，指出衝突，不自行猜測。
2. 理解系統架構、實際功能需求、部署方式、外部介面、支援的平台與相容性要求。
3. 檢查 Git 工作目錄與分支狀態，辨識尚未提交的使用者修改。不得覆蓋、重置或清除這些修改。
4. 辨識主要執行入口，以及動態載入、反射、插件註冊、依賴注入、序列化、公開 API、CLI、背景工作、資料庫遷移與外部整合。
5. 不得僅因為搜尋不到直接呼叫，就判斷程式碼沒有用途。

## 第二階段：深度稽核（唯讀）

檢查以下候選問題：

- 不再使用的函式、類別、模組、檔案與資源。
- 已失效的實驗性程式碼、功能開關與條件分支。
- 可證實為重複、且無必要差異的實作。
- 不再使用的套件、設定、腳本與建置產物引用。
- 已不再需要的相容性處理或過時整合。
- 重複且不提供額外功能、邊界情況或回歸保護的測試。
- 明確失效的測試、測試輔助程式與固定資料。
- 可安全簡化、而不改變可觀察行為的複雜邏輯。

必要時可使用子代理並行進行**互不重疊的唯讀分析**，但避免重複掃描、無意義的代理呼叫與不必要的 Token 消耗。不要讓多個代理同時修改同一批檔案。

## 第三階段：證據與風險分類（唯讀）

對每個候選清理項目提供：

1. 檔案路徑、符號名稱與具體位置。
2. 判定無用、過時或冗餘的**可查證證據**，並區分「直接觀察」與「推論」。
3. 已檢查的直接與間接參照：呼叫圖、搜尋、設定檔、測試、建置、部署與外部契約；說明尚未能檢查的部分。
4. 對動態入口、公開 API、CLI、外部消費者、資料格式、持久化資料、向下相容性的可能影響。
5. 預期清理效益與最壞情況的風險。
6. 清理前後如何驗證，以及可操作的回復方式。

風險分類：

- **低風險：** 具充分、可重現的證據；已合理排除重要依賴。
- **中風險：** 有清理價值，但依賴或行為仍須補充驗證。
- **高風險：** 涉及核心路徑、公開介面、動態載入、相容性或未知外部使用情境。

無法證明安全的項目必須保留；不要把「缺乏證據」當作「無人使用」。

## 第四階段：先提案、後執行

先提供完整稽核摘要與分批清理計畫，列明每批的檔案、理由、風險、驗證與回復方式。

**在我明確批准具體清理範圍前，不得刪除程式碼、測試、設定或檔案，也不得進行任何破壞性清理。** 可先提出建議，但不得自行將提案視為批准。若本次任務僅要求稽核，停留在報告階段。

取得批准後：

1. 只改動獲批准的範圍；新增問題另外列出，不自動擴大清理。
2. 採取小批次、最小必要、容易以 Git diff 審查及回復的變更。
3. 避免順手重構無關程式碼，不更改既有功能與對外契約。
4. 遇到真正的 Bug，修復根本原因；不得刪除失敗測試、跳過測試或削弱斷言來掩飾問題。
5. 不將減少測試數量或覆蓋率當成目標；保留邊界情況、錯誤處理、回歸與整合測試的價值。
6. 不得使用會丟失工作成果的 Git 操作（例如未經批准的 reset、clean、force push）；不要自行提交、推送或合併，除非我明確要求。
7. 如發現新的高風險事項或測試基準異常，停止受影響範圍的修改並回報。

## 第五階段：精準驗證與成本控制

1. 先確認受影響測試、靜態檢查與建置的基準狀態，標註既有失敗。
2. 優先執行與修改直接相關的必要測試與檢查。
3. 只有在跨模組風險、發布規範或變更性質需要時，才擴大至整合或完整測試；不得擅自跳過專案要求的必跑檢查。
4. 同一組未變動條件下不重複執行無資訊價值的測試；重跑時說明新假設或新變更。
5. 失敗時先分析日誌與原因，區分原有失敗、新增回歸及環境問題，不要盲目重跑。
6. 不得為了測試通過而削弱斷言、隱藏錯誤、關閉檢查或降低品質門檻。
7. 若受限於依賴、硬體、憑證或環境而未能驗證，明確註明「未驗證」及原因，不得宣稱通過。

## 第六階段：成果報告

提供以下內容：

- 稽核範圍及沒有涵蓋的部分。
- 候選問題、證據、風險分類及處置建議。
- 已批准且實際變更的項目與理由（如果尚未批准，明確寫「尚未修改」）。
- 保留項目及原因，尤其是存在不確定性的項目。
- 程式碼、測試、依賴、設定的實際變更摘要及 Git diff 摘要。
- 執行的檢查、基準狀態、結果與未驗證範圍。
- 尚未解決的風險與建議後續步驟。

**成功標準：改善可維護性、保留必要行為與測試保障、降低回歸風險，並合理控制 Token、代理與測試成本；不是刪除最多行數。**
